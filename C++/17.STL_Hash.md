`std::unordered_set` 和 `std::unordered_map` 是 C++ 标准模板库 (STL) 中非常强大且常用的关联容器。它们在底层完全抛弃了传统的树状结构，转而使用**哈希表 (Hash Table)** 来实现。它们最大的优势在于极致的速度：在理想情况下，插入、删除和查找的时间复杂度都能达到 $O(1)$，这使得它们在处理海量数据的快速检索时效率极高。

# 一、`unordered_set` (无序集合)

`std::unordered_set` 是定义在 `<unordered_set>` 头文件中的关联容器。它包含一组**唯一**的、类型为 Key 的对象。它的核心特征在于：**不排序**，但提供**平均常数时间（$O(1)$）**的搜索、插入和移除操作。

## 1.1 完整的模板参数定义

官方文档中，`std::unordered_set` 的完整模板签名包含四个参数（通常我们只用第一个，后三个有默认值）：

```C++
template<
    class Key,
    class Hash = std::hash<Key>,
    class KeyEqual = std::equal_to<Key>,
    class Allocator = std::allocator<Key>
> class unordered_set;
```

- **`Key`**: 存储的元素类型。
- **`Hash`**: 哈希函数对象类型。默认使用 `std::hash<Key>`。它的作用是将 Key 映射成一个 `size_t` 类型的哈希值。
- **`KeyEqual`**: 等价比较谓词。默认使用 `std::equal_to<Key>`（即 `==` 运算符）。当两个元素的哈希值相同时（发生哈希冲突），容器必须用它来判断这两个元素是否真的相等。
- **`Allocator`**: 内存分配器，通常不需要关心。

**关键点：** 如果你想把**自定义的结构体或类**（例如在处理数据时的自定义数据帧）放入 `unordered_set`，你必须自己提供 `Hash` 函数和 `KeyEqual`（重载 `==` 运算符），否则编译器会报错。

## 1.2 核心操作与时间复杂度

根据官方文档规定，操作的时间复杂度如下：

| **操作分类** | **常用函数**       | **平均复杂度** | **最坏复杂度** | **说明**                                                     |
| ------------ | ------------------ | -------------- | -------------- | ------------------------------------------------------------ |
| **查找**     | `find(key)`        | $O(1)$         | $O(N)$         | 返回指向元素的迭代器，未找到返回 `end()`。                   |
|              | `count(key)`       | $O(1)$         | $O(N)$         | 返回 1（存在）或 0（不存在）。                               |
|              | `contains(key)`    | $O(1)$         | $O(N)$         | **(C++20 引入)** 返回 `bool`，比 `count` 语义更清晰。        |
| **修改**     | `insert(val)`      | $O(1)$         | $O(N)$         | 插入元素。如果元素已存在，则什么也不做。                     |
|              | `emplace(args...)` | $O(1)$         | $O(N)$         | **原位构造**元素，比 `insert` 少一次拷贝/移动操作，性能更好。 |
|              | `erase(key)`       | $O(1)$         | $O(N)$         | 通过键值或迭代器删除元素。                                   |

*注：最坏复杂度 $O(N)$ 发生在极端哈希冲突的情况下，即所有元素都被哈希到了同一个“桶”中，退化成单链表。*

## 1.3 底层架构：桶接口

| **接口名称**             |  **核心返回值 / 功能**                          | **典型应用与注意事项**                                       |
| ------------------------ |  ---------------------------------------------- | ------------------------------------------------------------ |
| **`bucket_count()`**     |  返回当前底层实际分配的**桶的总数**。           | 观察容器扩容（Rehash）最直观的指标。                         |
| **`max_bucket_count()`** |  返回系统允许分配的**最大桶数**上限。           | 理论极值，通常受限于系统内存，日常极少触及。                 |
| **`bucket_size(n)`**     | 返回索引为 `n` 的**桶内包含的元素个数**。      | 用于**诊断哈希冲突严重程度**。如果某个桶的值特别大，说明哈希函数设计不佳。 |
| **`bucket(key)`**        |  返回键 `key` **所在的桶的索引**。              | 追踪特定数据被映射到了底层的哪个物理位置。                   |
| **`load_factor()`**      | 返回**当前负载因子** (`size / bucket_count`)。 | 衡量哈希表拥挤程度的核心指标。                               |
| **`max_load_factor()`**  |  获取或设置**最大负载因子**阈值（默认 1.0）。   | 决定容器何时自动扩容的关键边界，一般不建议修改。             |
| **`reserve(n)`**         | 预分配内存，准备**容纳 `n` 个元素**。          | **性能优化首选**。提前计算并分配足够桶数，避免插入时卡顿。   |
| **`rehash(n)`**          | 强制底层的**桶数至少为 `n`**。                 | 直接干预底层内存结构，通常用 `reserve` 替代。                |

```C++
// 辅助函数：打印容器当前的哈希策略和桶状态
void print_hash_status(const unordered_set<int>& my_set, const string& msg) 
{
	cout << "--- " << msg << " ---" << endl;
	cout << "当前元素个数 (size)         : " << my_set.size() << endl;
	cout << "当前桶的总数 (bucket_count) : " << my_set.bucket_count() << endl;
	cout << "当前负载因子 (load_factor)  : " << my_set.load_factor() << endl;
	cout << "最大负载因子 (max_load_factor): " << my_set.max_load_factor() << endl;
	cout << endl;
}

int main() 
{
	unordered_set<int> signature_ids;

	// 初始状态
	print_hash_status(signature_ids, "刚初始化的空容器");
	cout << "理论最大桶数: " << signature_ids.max_bucket_count() << "\n\n";

	// reserve 性能优化 
	signature_ids.reserve(100);
	print_hash_status(signature_ids, "调用 reserve(100) 之后");

	// 插入数据
	for (int i = 0; i < 50; ++i)
		signature_ids.insert(i * 10);
	print_hash_status(signature_ids, "插入50个元素后(未触发自动扩容)");

	// 定位特定元素与诊断哈希冲突
	int test_id = 200;
	// 获取该 ID 被分配到了哪个桶
	size_t target_bucket = signature_ids.bucket(test_id);
	cout << "特征 ID [" << test_id << "] 被分配到了桶号: " << target_bucket << endl;

	// 检查该桶里挤了多少个元素（有几个发生了哈希冲突）
	cout << "桶号 [" << target_bucket << "] 内部挂载的元素个数 (bucket_size): "
		<< signature_ids.bucket_size(target_bucket) << endl;

	// 遍历所有桶，寻找是否存在严重的哈希冲突 (单桶元素过多)
	int max_collisions = 0;
	for (size_t i = 0; i < signature_ids.bucket_count(); ++i) 
		if (signature_ids.bucket_size(i) > max_collisions) 
			max_collisions = signature_ids.bucket_size(i);

	cout << "当前所有桶中，最严重的冲突个数为: " << max_collisions << " (理想状态是 1)\n\n";

	// 触发底层的 Rehash
	signature_ids.rehash(500);
	print_hash_status(signature_ids, "强制调用rehash(500)之后");
	return 0;
}
```

# 二、`unordered_map` (无序映射/哈希表)

`std::unordered_map` 是定义在 `<unordered_map>` 头文件中的关联容器。它包含一组由**唯一的键 (Key)** 和**映射值 (Value)** 组成的键值对 (Key-Value pairs)。它的底层依然是**哈希表 (Hash Table)**，这使得它在平均情况下拥有 $O(1)$ 的查找、插入和删除时间复杂度。

## 2.1 完整的模板参数与底层节点

官方文档中，`std::unordered_map` 的完整模板签名包含五个参数：

```C++
template<
    class Key,
    class T,
    class Hash = std::hash<Key>,
    class KeyEqual = std::equal_to<Key>,
    class Allocator = std::allocator< std::pair<const Key, T> >
> class unordered_map;
```

- **`Key`**: 键的类型。
- **`T`**: 映射值的类型。
- **`Hash` / `KeyEqual`**: 与 `unordered_set` 相同，分别掌管哈希函数的计算和哈希冲突时的相等性判断。
- **`Allocator` (核心注意点)**: 注意看分配器里的类型，它是 `std::pair<const Key, T>`。这意味着在容器内部，键和值被打包成了一个 `pair`。**键是 `const` 的**，这意味着你不能修改一个已经存在于 Map 中的键（因为修改键会改变它的哈希值，破坏底层哈希表结构），你只能修改它的值 `T`。

## 2.2 核心操作

在 `unordered_map` 的日常使用中，把数据“放进去”或“改掉”是最频繁的操作。C++ 提供了几种不同的接口来完成这件事，它们在**“键（Key）已存在”**和**“键不存在”**时的行为差异巨大。

| **接口 / 操作符**                | **当 Key 不存在时**    | **当 Key 已存在时**            | **核心特征与评价**                             |
| -------------------------------- | ---------------------- | ------------------------------ | ---------------------------------------------- |
| **`map[key] = value`**           | **插入**新的键值对。   | **覆盖（修改）**原有的 Value。 | 最直观，但有“幽灵插入”的陷阱（见下文）。       |
| **`map.insert({k, v})`**         | **插入**新的键值对。   | **什么都不做**（拒绝覆盖）。   | 行为保守，保护已有数据不被意外篡改。           |
| **`map.emplace(k, v)`**          | **原地构造**新键值对。 | **什么都不做**（拒绝覆盖）。   | `insert` 的性能升级版，省去临时对象拷贝。      |
| **`map.insert_or_assign(k, v)`** | **插入**新的键值对。   | **覆盖（修改）**原有的 Value。 | **C++17 引入**，语义最明确的“插入或更新”利器。 |

`operator[]` 是极其强大的双刃剑，它既能**读**，也能**写**，但它的底层逻辑是：**只要你调用了它，它就必须给你返回一个有效的 Value 引用。**

- **赋值行为：** `my_map["apple"] = 10;`
	- 如果 `"apple"` 存在，直接把它的值改成 `10`。
	- 如果 `"apple"` 不存在，它会先创建一个 `{"apple", 0}`（Value 被默认初始化），然后再把 `0` 赋值为 `10`。这很符合直觉。
- **读取行为（致命陷阱）：** `int count = my_map["banana"];`
	- 在 C++ 的 `unordered_map` 中，**如果你去读取一个不存在的 Key，它会悄悄地在容器里插入一个默认值，并把这个默认值返回给你！**
	- 结果是：`count` 变成了 `0`，而你的 `my_map` 里意外多出了一个脏数据 `{"banana", 0}`。

**正确姿势：** 绝对不要用 `[]` 来检查元素是否存在。只在明确想赋值，或者做频率统计（如 `my_map["word"]++`）时使用它。只读操作请使用 `.at(key)`（不存在时会抛异常）或 `.find(key)`。

`insert()` 与 `emplace()`这两个接口的共同点是：**先入为主**。如果 Key 已经在容器里了，它们会立刻放弃操作，**绝对不会覆盖**原有的 Value。

- **`insert()`：** 需要传入一个组装好的 `std::pair` 对象。

	```C++
	my_map.insert(make_pair("apple", 10)); // 传统写法
	my_map.insert({"banana", 20});         // C++11 列表初始化写法
	```

- **`emplace()`：** 性能更高。你不需要打包 `pair`，直接把 Key 和 Value 的构造参数传进去，容器会在底层直接分配内存并原地构造对象。**在实际工程中，几乎总是推荐用 `emplace` 替代 `insert`。**

	```C++
	my_map.emplace("cherry", 30); 
	```

	*(注意：如果 `"cherry"` 已经存在，这行代码执行后，原来的值不会变。)*

## 2.3 底层接口

`std::unordered_map` 的底层桶管理和哈希策略与 `std::unordered_set` **完全一模一样**。

前文讲解的 8 个接口：`bucket_count`, `bucket_size`, `load_factor`, `reserve`, `rehash` 等等，在这里的用法和性能优化逻辑完全适用。**在处理大规模键值对映射前，务必先调用 `reserve()`**。

```C++
// 辅助打印函数
void print_map(const unordered_map<string, int>& m, const string& msg) 
{
	cout << "--- " << msg << " ---" << endl;
	for (const auto& pair : m) 
		cout << "[" << pair.first << "] = " << pair.second << endl;
	cout << "当前容器大小: " << m.size() << "\n\n";
}

int main() 
{
	unordered_map<string, int> my_map;

	// operator[]：赋值与“幽灵插入”陷阱
	// (1) Key 不存在时：正常插入新键值对
	my_map["apple"] = 10;
	print_map(my_map, "使用 [] 插入 apple=10");
	// (2) Key 已存在时：直接覆盖旧值
	my_map["apple"] = 20;
	print_map(my_map, "使用 [] 将 apple 修改为 20 (覆盖成功)");

	// (3) 【致命陷阱】试图只读一个不存在的 Key！
	// 原本只想看看有没有 "ghost"，结果 [] 悄悄插入了 {"ghost", 0}
	int ghost_val = my_map["ghost"];
	cout << "试图读取不存在的 ghost，得到的值是: " << ghost_val << endl;
	print_map(my_map, "读取 ghost 后的容器状态 (注意多了一个脏数据)");

	// 2. 测试 insert()：保守派，拒绝覆盖
	// (1) Key 不存在时：正常插入 (C++11 支持列表初始化语法)
	my_map.insert({ "banana", 30 });
	print_map(my_map, "使用 insert 插入 banana=30");
	// (2) Key 已存在时：什么都不做，拒绝覆盖
	my_map.insert({ "banana", 999 });
	print_map(my_map, "试图用 insert 将 banana 修改为 999 (修改失败，保留 30)");


	my_map["banana"] = 40; // 即使 banana 是由 insert 创建的，[] 依然可以强行修改它
	print_map(my_map, "使用 [] 强行修改 banana 为 40");

	return 0;
}
```

1. **永远不要用 `operator[]` 来做“存在性检查”**：如果想知道一个 Key 存不存在，用 `find()`，或者 C++20 的 `contains()`，或者 `count()`。如果你写了 `if (myMap["key"] == 1)`，即使 "key" 原本不存在，这行代码执行后，容器里也会多出一个无用的 `{"key", 0}` 数据，这往往是内存泄漏或逻辑 bug 的源头。
2. **自定义 Key 的要求**：如果你想用自定义结构体作为 Key，你依然需要像 set 那样，提供自定义的哈希函数和重载 `==` 运算符。

# 三、它们与 `set` / `map` 的区别

它们的名字只有一词之差，但底层逻辑、性能表现和适用场景却截然不同。它们的根本分歧在于**底层数据结构**：

- **`unordered_set` / `unordered_map`**：底层是**哈希表 (Hash Table)**。
- **`set` / `map`**：底层通常是**红黑树 (Red-Black Tree)**，一种自平衡二叉查找树。

## 3.1 差异对比

| **特性**             | **unordered_set / unordered_map (哈希表)**        | **set / map (红黑树)**                           |
| -------------------- | ------------------------------------------------- | ------------------------------------------------ |
| **元素是否有序**     | **绝对无序** (随哈希值和扩容而变)                 | **严格有序** (默认升序排列)                      |
| **平均时间复杂度**   | **$O(1)$** (极快)                                 | **$O(\log n)$** (较快)                           |
| **最坏时间复杂度**   | $O(n)$ (发生极端哈希冲突时)                       | $O(\log n)$ (性能极其稳定)                       |
| **内存开销**         | 较高 (需维护哈希桶数组及冲突链表，常有空闲桶)     | 适中 (每个节点需额外存储父/子节点指针和颜色标记) |
| **自定义类型的要求** | 需提供自定义 **Hash 函数** 和重载 **`==` 运算符** | 需重载 **`<` 运算符** (或提供 Compare 函数)      |
| **迭代器类型**       | 前向迭代器 (Forward Iterator)                     | 双向迭代器 (Bidirectional Iterator)              |

## 3.2 深入理解关键差异

**1. 性能的“爆发力”与“稳定性”**

- **哈希容器**是追求“爆发力”的极客。在预留了足够空间（调用 `reserve`）且哈希函数优秀的情况下，它的增删查操作能做到瞬间完成 ($O(1)$)。但在极其偶然的情况下，或者未提前规划内存导致触发大范围 `Rehash` 时，会出现明显的性能抖动 ($O(n)$)。
- **树形容器**则是追求“稳定性”的优等生。红黑树的高度始终是对数级别的，无论你插入什么极端数据，它的查找和插入永远稳定在 $O(\log n)$。

**2. 顺序与区间操作**

- **树形容器 (map/set)** 因为天然有序，支持极其强大的**边界查询**操作。比如 `lower_bound()` 和 `upper_bound()`，可以在树中快速找到“第一个大于等于 X 的元素”或“第一个大于 X 的元素”。
- **哈希容器**对顺序一无所知，完全无法进行范围查询或排序输出。

## 3.3 选型指南

在实际项目开发中，选择容器的黄金法则是：**优先使用 `unordered_map/set`，除非你有必须使用 `map/set` 的理由。**

### 场景 1：无脑首选 `unordered_map` / `unordered_set`

绝大多数只涉及到**“匹配”、“去重”、“频次统计”**的场景，都应该用无序容器。

- **海量特征去重或查找：** 在处理数百万个样本的 ID 或离散特征进行去重。使用 `unordered_set` 配合 `reserve` 可以在极短时间内完成，而红黑树会在此类海量数据下因频繁的树节点旋转而显得非常吃力。
- **建立数据映射字典：** 将分类标签映射为整数索引，直接使用 `unordered_map<string, int>` 能提供最快的查询映射速度。
- **缓存 (Cache) 系统：** 存储已计算过的结果，以输入参数为 Key，计算结果为 Value，需要极致的单点查询速度。

### 场景 2：必须使用标准的 `map` / `set`

当你遇到了以下三种需求之一时，果断放弃哈希容器，转向红黑树：

1. **需要数据始终保持排序状态**，如果你不仅需要存储数据，还需要时不时地“按大小顺序遍历输出”，或者获取数据时的要求是“输出前 10 个最大的特征”。`set` 会在每次插入时自动为你排好序。
2. **需要进行范围查找 (Range Query)**，在 `map` 中，可以用 `map.lower_bound()` 瞬间锁定位置。在 `unordered_map` 中，只能绝望地从头到尾遍历整个容器。
3. **对时间抖动极其敏感，不能容忍 $O(n)$**，在严格的实时系统中，哈希表偶尔触发的 `Rehash` 延迟是不可接受的。红黑树严格的 $O(\log n)$ 保证了系统响应时间的确定性。
4. **无法构造合适的 Hash 函数**，如果你想将一个非常复杂的对象作为 Key，但很难为它设计一个既均匀又高效的 Hash 函数，而比较两个对象的大小（重载 `<`）却很容易，那么使用 `map`/`set` 会省去很多麻烦。

# 四、哈希冲突

## 4.1 哈希函数设计理论

哈希函数的终极目标是：**将不可预知的输入，极其均匀地“打散”到有限的数组空间中。**

### 4.1.1 除法散列法

这是最基础、应用最广的方法。

- **数学本质：** 利用模运算（求余数）将任意大的整数映射到一个固定范围 $[0, M-1]$ 内。公式为 $h(key) = key \pmod M$。
- **为何必须是质数：** 假设我们正在处理一个**签名识别**任务，提取出了一大批签名的特征 ID，并且这些 ID 可能是按某种规律生成的（例如 100, 200, 300...）。如果我们的哈希表大小 $M = 100$（不是质数，且是 10 的倍数），那么 $100 \pmod{100}$、$200 \pmod{100}$ 的结果全是 $0$。这会导致所有数据极其惨烈地堆积在第 0 号桶中。
- **破局点：** 如果把 $M$ 设为一个质数，比如 $101$。那么 $100 \pmod{101} = 100$，$200 \pmod{101} = 99$，$300 \pmod{101} = 98$。原本呈现出规律性的倍数数据，被质数除完之后，余数会被彻底打乱，均匀散布在表中。

### 4.1.2 乘法散列法

这种方法对哈希表的大小 $M$ 没有任何限制（比如 $M$ 可以直接取 2 的幂，方便计算机进行底层位运算），它完全依靠小数的乘法来制造“混乱”。

- **数学本质：** 公式为 $h(key) = \lfloor M(key \cdot A \pmod 1) \rfloor$。这里的 $A$ 是一个介于 0 和 1 之间的小数（通常取黄金分割比 $0.618...$）。$(key \cdot A \pmod 1)$ 的意思是，乘完之后**只保留小数部分**。
- **直观例子：**连续的整数经过除法散列可能会映射到连续的桶里。但在乘法散列中，由于我们乘以了一个无理数（黄金分割比）并只取小数部分，即使是相邻的输入 `key=1` 和 `key=2`，它们的小数部分也会发生剧烈的跳跃，再乘以 $M$ 后，它们会被分配到相隔极远的桶中。

### 4.1.3 全域散列法

这是一种建立在“概率论”和“博弈论”基础上的防御性策略。

- **数学本质：** 我们不写死一个哈希函数，而是准备了一个庞大的“哈希函数库”：$h_{a,b}(key) = ((a \cdot key + b) \pmod P) \pmod M$。每次程序启动或初始化哈希表时，系统利用随机数生成器，随机挑一组 $a$ 和 $b$。
- **解决的痛点（恶意攻击）：** 假设你公开了一个数据接口，如果攻击者知道你用的是固定的除法散列 $h(key) = key \pmod{100}$，他就可以故意构造出 100, 200, 300 这样的恶意数据流发送给你，让你的哈希表瞬间退化成单链表，导致 CPU 占用率飙升 100%（即 DoS 拒绝服务攻击）。全域散列让攻击者根本猜不到你这次运行使用的是哪组参数，从概率上彻底封死了这种极端情况。

## 4.2 哈希冲突处理理论

由于“鸽巢原理”（鸽子多，鸽巢少），冲突是绝对无法避免的。处理冲突的核心思想就是：**当原本属于你的位置被别人占了，你该怎么找下一个位置？**

### 4.2.1 开放定址法

开放定址法的核心是“所有数据必须全塞在一个大数组里”。

- **线性探测**
	- **理论：** 如果 $hash_0$ 满了，就看 $hash_0 + 1$，再满就看 $hash_0 + 2$，遇到数组尾部就绕回头部。
	- **致命缺陷（一次群集）：** 就像在拥挤的停车场找车位。如果 5 号车位被占了，你就停 6 号。下一个目标是 5 号的车来了，发现 5 和 6 都满了，只能停 7 号。久而久之，5 到 10 号会连成一大片“拥堵区”，后来的人哪怕原本应该停在 8 号，也不得不越过整个拥堵区去停 11 号。这导致性能急剧下降。
- **二次探测**
	- **理论：** 如果 $hash_0$ 满了，就往两边跳着找。第一次跳 $1^2$，第二次跳 $2^2$（即跨度为 4），第三次跳 $3^2$（跨度为 9）。
	- **优势：** 这就像找车位时，如果 5 号满了，你直接开车去 6 号看看，如果还满，你一脚油门开到 9 号看看。这立刻打破了连成一片的“拥堵区”。
- **双重散列**
	- **理论：** 遇到冲突时，利用**第二个哈希函数** $h_2(key)$ 专门为你计算出一个专属步长。探测序列变为 $hash_0 + 1 \cdot h_2(k)$, $hash_0 + 2 \cdot h_2(k)$...

### 4.2.2 链地址法

这就是 C++ 中 `std::unordered_map` 和 `std::unordered_set` 底层真正使用的方法。

- **理论本质：** 数组里存的不再是数据本身，而是一排“钩子”（指针）。当多个数据映射到同一个下标时，我们不在数组里找空位了，而是直接在这个位置上“挂一根绳子”（单链表），把所有冲突的数据像串糖葫芦一样串起来。
- **优雅的降级机制：** 开放定址法一旦数据满了，程序就彻底崩溃了。而链地址法哪怕数据量超过了桶的数量，它依然能运行，只是每根绳子变得更长了而已。
- **现代工程的极致优化：** 为了防止某根链表过长（查找效率退化为 $O(N)$），现代语言（如 Java 8）会在底层增加一个监控：当链表的长度达到 8 个节点时，算法会自动将这根链表“折叠”成一棵**红黑树 (Red-Black Tree)**。这样，即使发生了极端严重的冲突，查找时间也能被强行控制在 $O(\log n)$ 的极速范围内。

## 5.1 底层支撑

### 5.1.1 仿函数提取 Key 与 BKDR 字符串哈希

哈希表底层是一个数组，所以必须将任意类型的 Key 转化为数组下标 (`size_t`)。

- **泛型 `HashFunc<K>`**：通过简单的 C 风格强制类型转换 `(size_t)key` 来处理整型、字符型等天生可以转为数字的类型。
- **特化 `HashFunc<string>`**：这是重点。你使用了业界著名的 **BKDR Hash** 算法。
	- **实现思路**：遍历字符串，将前一次的哈希值乘以 131，再加上当前字符的 ASCII 码。
	- **为什么是 131？** 这是一个经验质数（31, 131, 1313 等都可以）。乘以质数能将字符的位置权重指数级放大，完美解决 "abc" 和 "cba" 因字符相加之和相同而导致的严重冲突。

```c++
template<class K>
struct HashFunc
{
	size_t operator()(const K& key) { return (size_t)key; }
};

template<>
struct HashFunc<string>
{
	size_t operator()(const string& s)
	{
		size_t hash = 0;
		for (auto ch : s)
		{
			hash += ch;
			hash *= 131;
		}
		return hash;
	}
};
```

### 5.1.2 素数表容量控制

- **实现思路**：根据源码硬编码了一个大小约按 2 倍递增的质数表，并通过 `lower_bound`（底层是二分查找）快速获取下一个合适的质数作为哈希表的新容量。
- **重点详解**：为什么一定要用质数做容量？在使用除留余数法 (`hash % size`) 时，如果 `size` 是偶数（特别是 2 的幂），那些低位相同但高位不同的 Key 会大量发生冲突。质数作为除数，能最大程度打乱数据的倍数规律，让映射结果更均匀。

```c++
inline unsigned long __stl_next_prime(unsigned long n)
{
	// Note: assumes long is at least 32 bits.
	static const int __stl_num_primes = 28;
	static const unsigned long __stl_prime_list[__stl_num_primes] = {
		53, 97, 193, 389, 769,
		1543, 3079, 6151, 12289, 24593,
		49157, 98317, 196613, 393241, 786433,
		1572869, 3145739, 6291469, 12582917, 25165843,
		50331653, 100663319, 201326611, 402653189, 805306457,
		1610612741, 3221225473, 4294967291
	};
	const unsigned long* first = __stl_prime_list;
	const unsigned long* last = __stl_prime_list + __stl_num_primes;
	const unsigned long* pos = lower_bound(first, last, n);
	return pos == last ? *(last - 1) : *pos;
}inline unsigned long __stl_next_prime(unsigned long n)
{
	// Note: assumes long is at least 32 bits.
	static const int __stl_num_primes = 28;
	static const unsigned long __stl_prime_list[__stl_num_primes] = {
		53, 97, 193, 389, 769,
		1543, 3079, 6151, 12289, 24593,
		49157, 98317, 196613, 393241, 786433,
		1572869, 3145739, 6291469, 12582917, 25165843,
```

## 5.2 开放定址法实现 

开放定址法的核心理念是：**不借助外部链表，所有数据全塞在一个数组里。**

**1. 状态标记与伪删除**

- **思路**：定义了枚举 `State { EXIST, EMPTY, DELETE }`，并封装在 `HashData` 中。
- **重点**：这是开放定址法的灵魂。如果在 `Erase` 时直接把数据清空（变成 `EMPTY`），会导致后续因哈希冲突而存放在它后面的元素在 `Find` 时因为遇到 `EMPTY` 提前终止，从而“失联”。你将状态置为 `DELETE`，既宣告了该位置可用，又保证了探测路径的连贯性。

**2. 负载因子与扩容机制**

- **思路**：`if (_n * 10 / _tables.size() >= 7)`。你将负载因子的阈值严格卡在 $0.7$。
- **重点**：开放定址法极其害怕数组变满。一旦负载因子超过 0.7-0.8，哈希冲突的概率会呈指数级上升。你的扩容写得很优雅：直接创建一个新的 `HashTable`，利用现成的 `Insert` 接口将老表数据重新插入，最后用 `_tables.swap(newht._tables)` 偷天换日，代码复用性极高。

**3. 探测策略·**

- **二次探测 (Quadratic Probing)** 逻辑，步长交替为 $+1^2, -1^2, +2^2, -2^2 \dots$ (`hashi = (hash0 + (i * i * flag)) % _tables.size();`)。
- **线性探测 (Linear Probing)** 逻辑，步长为 $+1, +2, +3 \dots$ (`hashi = (hash0 + i) % _tables.size();`)。

```c++
//线性探测
hashi = (hash0 + i) % _tables.size();
i++;
```

```c++
//二次探测
hashi = (hash0 + (i * i * flag)) % _tables.size();
if (hashi < _tables.size())
    hashi += _tables.size();
if (flag == 1)
    flag = -1;
else
{
    ++i;
    flag = 1;
}
```
**完整代码：**

```c++
bool Insert(const pair<K, V>& kv)
{
    // 去重：哈希表中不允许存在相同的 Key。 复用 Find 接口，如果找到了相同的 Key，直接插入失败。
    if (Find(kv.first))
        return false;

    // 扩容检测：负载因子（Load Factor）控制 开放定址法极其依赖剩余空间，负载因子通常严格控制在 0.7 以下。 
    //这里将 _n / _tables.size() >= 0.7 两边同乘 10，转为整数运算防止浮点数精度丢失。
    if (_n * 10 / _tables.size() >= 7)
    {
        // 创建一个局部的全新哈希表对象
        HashTable<K, V, Hash> newht;
        // 计算下一个质数，并将新表底层的 vector 扩容到该大小
        newht._tables.resize(__stl_next_prime(_tables.size() + 1));
        // 遍历旧表，将所有有效数据（EXIST）重新映射到新表
        for (auto& data : _tables)
            // 只有状态为 EXIST 的数据才是真正需要保留的（跳过 EMPTY 和 DELETE）
            if (data._state == EXIST)
                // 直接复用 Insert 接口，此时新表肯定很空，不会再次触发扩容
                newht.Insert(data._kv);
        // 窃取新表的底层数组 交换后当前对象的 _tables 就变成了扩容后且重新映射完毕的新数组 而旧数组会被 newht 这个局部对象在函数结束时自动销毁。
        _tables.swap(newht._tables);
    }

    // 寻找落脚点
    Hash hash; // 实例化哈希仿函数对象
    // 计算基准下标 hash0（除留余数法）
    size_t hash0 = hash(kv.first) % _tables.size();
    size_t hashi = hash0; // hashi 用于探测时的游标
    size_t i = 1;
    int flag = 1;

    // 如果当前位置被有效数据占据，则发生哈希冲突，开始探测寻找空位 如果是 DELETE 状态，说明这里的数据被删除了，我们可以直接覆盖它，所以循环会跳出
    while (_tables[hashi]._state == EXIST)
    {
        // 线性探测：每次向后移动 1, 2, 3... 步长
        // 并在到达数组尾部时通过取模 % _tables.size() 自动回绕到头部
        hashi = (hash0 + i) % _tables.size();
        i++;
    }

    // 落盘：找到 EMPTY 或 DELETE 的位置，将数据写入并更新状态
    _tables[hashi]._kv = kv;
    _tables[hashi]._state = EXIST;
    ++_n; // 有效数据个数加 1
    return true;
}

HashData<K, V>* Find(const K& key)
{
    Hash hash;
    size_t hash0 = hash(key) % _tables.size();
    size_t hashi = hash0;
    size_t i = 1;

    // 探测的终止条件是遇到 EMPTY。
    // 遇到 EXIST 说明有人，可能是我们要找的，也可能是发生冲突占位的，继续找。
    // 遇到 DELETE 说明这里的数据被删了，但它曾经被人占用过，真正的目标可能因为冲突被挤到了后面，必须穿透它继续找。
    while (_tables[hashi]._state != EMPTY)
    {
        // 找到了目标 Key，且该数据未被删除（状态不是 DELETE）
        if (_tables[hashi]._kv.first == key && _tables[hashi]._state != DELETE)
            return &_tables[hashi]; // 返回该节点指针
        // 线性探测：向后按顺序找（必须与 Insert 时的路径完全一致）
        hashi = (hash0 + i) % _tables.size();
        i++;
    }
    // 遇到了 EMPTY 还没找到，说明该 Key 绝对不存在于表中
    return nullptr;
}

bool Erase(const K& key)
{
    // 先复用 Find 接口尝试找到目标数据
    HashData<K, V>* ret = Find(key);
    if (ret)
    {
        // 伪删除（延迟删除）
        // 绝对不能把状态重置为 EMPTY，否则会导致哈希探测链断裂。
        // 比如：A、B、C 冲突，A 在 1 号，B 在 2 号，C 在 3 号。
        // 如果直接把 B 设为 EMPTY，下次 Find 去找 C 时，走到 2 号发现是 EMPTY 就会直接返回找不到。
        // 设为 DELETE 可以保证 Find 找 C 的时候穿透过去。
        ret->_state = DELETE;

        // 注意：在这个版本的实现中，Erase 后 _n 没有 --。
        // 因为 DELETE 状态的位置实际上还是占据着哈希表的“坑位”，
        // 如果将 _n 减去，可能会导致坑位被占满但负载因子没达标，引发死循环。
        return true;
    }
    else
        return false; // 根本没找到，删除失败
}
```

> 必须保证 `Insert`、`Find` 和 `Erase` 使用完全相同的探测公式。建议统一改为简单的线性探测，或者把二次探测的逻辑同步到 `Find` 中。

## 5.2 链地址法/哈希桶

这是工程中最常用的实现方式（即 STL 的默认行为），解决了开放定址法容易拥堵的问题。

**1. 节点设计与头插法**

- **思路**：哈希表退化为一个指针数组 `vector<Node*> _tables`。遇到冲突时，使用**头插法** (`newnode->_next = _tables[hashi]; _tables[hashi] = newnode;`)。
- **重点**：头插法的时间复杂度是绝对的 $O(1)$，不需要遍历到链表尾部。同时它符合“时间局部性原理”：刚插入的数据更有可能被马上访问到，放在链表头部能提升命中速度。

```c++
size_t hashi = hash(kv.first) % _tables.size();
Node* newnode = new Node(kv);
newnode->_next = _tables[hashi];
_tables[hashi] = newnode;
++_n;
```

**2. 扩容时的节点转移**

- **思路**：当负载因子达到 $1$ (`_n == _tables.size()`) 时触发扩容。
- **重点**：直接遍历老表，**把老表中的现有节点“摘”下来，重新计算哈希值后，直接挂载到新表的对应链表上**。这种“只改指针，不挪内存”的转移方式，是工业级哈希桶扩容的标准优化做法。

```c++
if (_n == _tables.size())
{
    vector<Node*> newtable(__stl_next_prime(_tables.size() + 1));
    //vector<Node*> newtable(_tables.size() * 2);
    for (size_t i = 0; i < _tables.size(); i++)
    {
        Node* cur = _tables[i];
        while (cur)
        {
            //直接拿下来
            Node* next = cur->_next;
            size_t hashi = hash(cur->_kv.first) % newtable.size();
            cur->_next = newtable[hashi];
            newtable[hashi] = cur;
            cur = next;
        }
        _tables[i] = nullptr;
    }
    _tables.swap(newtable);
}
```

**3. 内存的严格回收 (`~HashTable`)**

- **思路**：编写了析构函数，双层循环遍历数组和每条链表。
- **重点**：因为数据都存在外部链表节点 (`new Node`) 中，`vector` 销毁时只会销毁指针本身。手动遍历并 `delete cur` 是绝对必要的，完美杜绝了内存泄漏问题。

```c++
~HashTable()
{
	for (size_t i = 0; i < _tables.size(); i++)
	{
		Node* cur = _tables[i];
		while (cur)
		{
			Node* next = cur->_next;
			delete cur;
			--_n;
			cur = next;
		}
		_tables[i] = nullptr;
	}
}
```

**完整代码：**

```c++
bool Insert(const pair<K, V>& kv)
{
	// 去重检查：哈希容器（除了 multimap/multiset）不允许键值(Key)重复 Find 接口，如果找到了相同的 Key，则拒绝插入
	if (Find(kv.first))
		return false;
	Hash hash; // 实例化哈希仿函数对象
	
	// 扩容逻辑：当负载因子达到 1 (即元素总数 == 桶的数量) 时触发扩容 哈希桶的负载因子可以大于 1，但为了保证 O(1) 的查询效率，通常在达到 1 时扩容
	if (_n == _tables.size())
	{
		// 创建一个全新的 vector 作为新表，大小取质数表中的下一个质数
		vector<Node*> newtable(__stl_next_prime(_tables.size() + 1));
		// 遍历旧表中的每一个桶
		for (size_t i = 0; i < _tables.size(); i++)
		{
			Node* cur = _tables[i]; // cur 指向当前桶的单链表头节点
			while (cur)
			{
				// 【绝佳的底层优化：节点原地复用】
				// 传统的扩容可能是调用 Insert(cur->_kv)，这会疯狂触发 new 和 delete。
				// 这里直接将原链表的物理节点“摘”下来，避免了海量内存分配的开销。
				Node* next = cur->_next; // 提前保存原链表的下一个节点，防止链表断裂
				
				// 重新计算该节点在扩容后新表中的桶号 (Rehash)
				size_t hashi = hash(cur->_kv.first) % newtable.size();
				
				// 【头插法】将节点挂载到新表的对应桶中
				cur->_next = newtable[hashi];
				newtable[hashi] = cur;
				
				cur = next; // 迭代处理原链表中的下一个节点
			}
			_tables[i] = nullptr; // 旧表的桶置空，防止野指针
		}
		// 用新表的底层数组替换旧表的底层数组。 局部变量 newtable 在作用域结束后会自动销毁它带走的那个原来太小的旧数组。
		_tables.swap(newtable);
	}

	// 正常插入逻辑
	// 计算新插入的 Key 在哈希表中的落脚点（桶号）
	size_t hashi = hash(kv.first) % _tables.size();
	// 为新数据在堆区申请一个物理节点
	Node* newnode = new Node(kv);
	// 【头插法】将新节点插入到对应桶的单链表最头部
	// 使用头插法不仅因为时间复杂度是 O(1)，而且符合“时间局部性原理”（刚刚写入的数据大概率马上会被访问到）
	newnode->_next = _tables[hashi];
	_tables[hashi] = newnode;
	++_n; // 维护哈希表内部的有效数据总个数
	return true;
}
Node* Find(const K& key)
{
	Hash hash;
	// 通过哈希函数和除留余数法，精准定位到对应的桶（即单链表的头指针）
	size_t hashi = hash(key) % _tables.size();
	Node* cur = _tables[hashi];
	// 顺着单链表往下遍历查找（解决哈希冲突的过程）
	while (cur)
	{
		// 比对当前节点的 Key 是否等于目标 Key
		if (cur->_kv.first == key)
			return cur; // 找到了，直接返回该节点的指针
		cur = cur->_next; // 没找到，顺藤摸瓜继续往下找
	}
	// 遍历完整个桶的链表都没找到，说明哈希表中绝对不存在该 Key
	return nullptr;
}
bool Erase(const K& key)
{
	Hash hash;
	// 定位到目标元素可能存在的桶号
	size_t hashi = hash(key) % _tables.size();
	
	// 准备遍历单链表 因为是单向链表，执行删除操作必须同时维护当前节点(cur)和前驱节点(prev)的指针
	Node* prev = nullptr;
	Node* cur = _tables[hashi];
	while (cur)
	{
		// 找到了要删除的目标节点
		if (cur->_kv.first == key)
		{
			// 情况 A：要删除的刚好是这个桶的第一个节点（头节点）
			// 此时 prev 还是 nullptr
			if (prev == nullptr)
				// 直接让哈希表数组的头指针跳过 cur，指向 cur 的下一个节点
				_tables[hashi] = cur->_next;
			// 情况 B：要删除的节点位于单链表的中间或尾部
			else
				// 将前驱节点的 next 绕过当前节点，直接连上当前节点的 next 从而在物理链表上将 cur 孤立出来
				prev->_next = cur->_next;
			
			// 真正的物理删除：释放节点在堆区的内存
			delete cur;
			cur = nullptr; // 防止野指针
			--_n;          // 维护有效数据个数
			
			return true;   // 斩草除根，删除成功
		}
		else
		{
			// 如果当前节点不是目标，双指针同步往后挪一步
			prev = cur;
			cur = cur->_next;
		}
	}
	// 整个链表都翻遍了还没找到，说明 Key 根本不在表里，删除失败
	return false;
}
```
